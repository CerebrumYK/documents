# ЗАКЛЮЧИТЕЛЬНЫЙ РАЗДЕЛ

## Принцип дальнейшей реализации и единая проектная документация

# 103. Общий подход к дальнейшей разработке

Все сформированные требования должны быть консолидированы в единую проектную документацию.

На текущем этапе основной результат работы — не непосредственная реализация отдельных функций, а формирование полного и непротиворечивого описания будущей системы, включающего:

1. Бизнес-логику.
2. Пользовательский опыт.
3. Функциональные требования.
4. Техническое представление.
5. Модель данных.
6. Правила взаимодействия между функциональными модулями.
7. Ограничения и проверки.
8. Требования к безопасности.
9. Требования к публикации.
10. Миграцию существующих данных.
11. Тестовые сценарии.
12. Критерии приёмки.
13. Последовательность будущей реализации.

Эта документация должна использоваться как единый источник требований при последующей разработке.

# 104. Принцип «Business → UX → Logic → Technology»

Каждая функция должна описываться на четырёх связанных уровнях.

## 104.1. Business

Необходимо определить:

* для чего существует функция;
* какую задачу актрисы, администратора, кастинг-директора или другого пользователя она решает;
* какой конечный результат должен получить пользователь;
* какие данные являются исходными;
* какие данные являются результатом;
* какие действия должны оставаться под контролем человека.

Пример:

**Эмоциональный ряд**

Бизнес-задача:

Предоставить кастинг-директору компактное представление эмоционального диапазона актрисы, не увеличивая PDF десятками отдельных фотографий.

Результат:

В актёрскую анкету попадает одно составное изображение и ссылка на полное эмоциональное портфолио.

---

# 105. Пользовательский опыт — UX

Для каждой функции необходимо определить полный пользовательский сценарий.

Описание должно отвечать не только на вопрос:

**«Что должна уметь система?»**

но и:

**«Как именно пользователь этим воспользуется?»**

Для каждого сценария должны быть определены:

* точка входа;
* последовательность действий;
* названия элементов интерфейса;
* обязательные поля;
* необязательные поля;
* состояния загрузки;
* состояния сохранения;
* предупреждения;
* блокирующие ошибки;
* подтверждения;
* предварительный просмотр;
* успешный результат;
* дальнейшее возможное действие.

# 106. Пример полного пользовательского сценария

Для эмоционального ряда сценарий должен быть зафиксирован следующим образом:

1. Администратор открывает «Эмоциональное портфолио».
2. Создаёт новую съёмку.
3. Указывает дату съёмки.
4. Добавляет оригинальные фотографии.
5. Открывает «Эмоциональный ряд».
6. Нажимает «Создать».
7. Выбирает исходную фотосессию.
8. Выбирает сетку, например 4×4.
9. Получает 16 пустых ячеек.
10. Для каждой ячейки выбирает фотографию.
11. Выполняет crop.
12. Формирует крупный план лица.
13. Подтверждает кадр.
14. Повторяет операцию для остальных ячеек.
15. Система проверяет готовность.
16. Администратор формирует единое изображение.
17. Проверяет результат.
18. Сохраняет.
19. При необходимости публикует.
20. В редакторе анкеты выбирает созданный эмоциональный ряд.
21. В PDF попадает одно изображение, дата съёмки и ссылка на полную фотосессию.

Такой уровень детализации должен применяться ко всем ключевым функциональным областям.

# 107. Бизнес-логика

Для каждого модуля необходимо отдельно зафиксировать бизнес-правила.

Бизнес-правила не должны зависеть от конкретного пользовательского интерфейса.

Например:

## Эмоциональный ряд

* создаётся только из фотографий конкретного профиля;
* создаётся только из существующих оригинальных фотографий;
* оригинальные изображения не изменяются;
* допускается только геометрический crop;
* дата съёмки обязательна;
* завершение невозможно при неподтверждённых ячейках;
* опубликованная анкета использует готовую производную версию.

## Контакты

* хранится единый справочник;
* видимость на сайте и в анкете независима;
* закрытые контакты не передаются браузеру;
* конкретная анкета имеет собственный набор контактов.

## Кастинг

* не является профессиональным проектом актрисы;
* требования кастинга и данные профиля хранятся раздельно;
* ИИ не имеет права придумывать отсутствующие факты;
* рекомендации требуют подтверждения;
* созданная анкета остаётся черновиком.

## Обратная связь

* сообщение сохраняется до отправки внешних уведомлений;
* ошибка WhatsApp не влияет на сохранение;
* входящее сообщение не является кастингом автоматически;
* кастинг создаётся только после действия администратора.

## Тема сайта

* ИИ создаёт проект оформления;
* ИИ не публикует тему;
* содержимое сайта не изменяется вместе с темой;
* оригинальные фотографии не модифицируются;
* публикация темы требует предварительной проверки.

```text
        ↓

        ↓
```

# 110. Модель состояния объектов

Для сущностей с жизненным циклом необходимо явно описывать состояния и допустимые переходы.

Например:

## Анкета

```text
Draft
  ↓
Ready
  ↓
Published
  ↓
Archived
```

Редактирование опубликованной версии не изменяет её напрямую.

Создаётся новая revision.

## Тема сайта

```text
Draft
  ↓
Ready
  ↓
Published
  ↓
Archived
```

Rollback создаёт новую revision на основании предыдущего snapshot.

## Обращение

```text
New
  ↓
In Progress
  ↓
Waiting Information / Waiting Decision
  ↓
Reply Sent
  ↓
Completed
```

Дополнительно:

```text
Rejected
Spam
Archived
```

# 111. Разделение исходных данных и производных результатов

Документация должна чётко различать:

## Source

Исходный пользовательский материал.

Например:

* фотография;
* текст кастинга;
* документ;
* контакт;
* описание профиля.

## Configuration

Параметры использования source.

Например:

* crop;
* порядок;
* checkbox включения;
* layout;
* PDF configuration.

## Derived

Автоматически сформированный результат.

Например:

* emotional grid;
* web image;
* PDF image;
* PDF questionnaire;
* AI recommendation;
* theme proposal.

Source не должен изменяться при изменении Derived.

---

# 112. Разделение факта и ИИ-рекомендации

В документации необходимо зафиксировать принцип:

```text
Source Fact
≠
AI Extraction
≠
AI Recommendation
≠
Human Decision
```

Пример:

```text
Source:
«Требуется английский B1»

AI Extraction:
language=English
minimumLevel=B1

Profile:
English=B2

AI Recommendation:
Include languages section

Human Decision:
Approved
```

Все четыре уровня должны храниться отдельно там, где это необходимо для аудита и повторной проверки.

# 113. Единый принцип ИИ-функций

ИИ должен использоваться как помощник.

ИИ может:

* анализировать;
* структурировать;
* сопоставлять;
* предлагать;
* формировать черновик;
* предлагать визуальное оформление.

ИИ не должен без подтверждения:

* изменять профиль;
* изменять профессиональные факты;
* публиковать контент;
* отправлять анкету;
* публиковать контакт;
* изменять внешность;
* публиковать тему;
* принимать решение об участии в кастинге.

```text
Implements:
BR-EMO-001
BR-EMO-002
UF-001

Documentation:
docs/modules/emotional-grid.md
```

---

# 129. Definition of Ready

Задача готова к разработке только если:

* понятна бизнес-цель;
* определён пользовательский сценарий;
* определён Scope;
* определён Out of Scope;
* известны зависимости;
* определены изменения данных;
* определена серверная логика;
* определена UI-логика;
* определены ошибки;
* определены критерии приёмки;
* определены необходимые тесты.

Если эти условия не выполнены, задача считается недостаточно подготовленной для разработки.

---

# 130. Definition of Done

Задача считается завершённой только если:

1. Реализована бизнес-логика.
2. Реализована серверная валидация.
3. Реализован интерфейс.
4. Реализованы необходимые права.
5. Обработаны error cases.
6. Добавлена migration, если требуется.
7. Добавлены unit tests.
8. Добавлены integration tests.
9. Добавлен E2E сценарий, если функция пользовательская.
10. Проверена accessibility.
11. Проверена совместимость с существующим функционалом.
12. Обновлена документация.
13. Acceptance criteria выполнены.

---

# 131. Приоритет источников требований

При будущей реализации следует использовать следующий порядок приоритета:

```text
1. Утверждённая бизнес-логика
2. Утверждённые функциональные требования
3. Утверждённый UX flow
4. Техническая спецификация
5. Acceptance criteria
6. GitHub Issue
7. Текущая реализация
```

Если существующий код противоречит утверждённой документации, это должно рассматриваться как различие между текущим и целевым состоянием, а не как основание автоматически изменить требования.

---

# 132. Управление изменениями требований

Новые пожелания в дальнейшем не должны добавляться только как сообщение или отдельный Issue.

Процесс:

```text
Новое пожелание
 ↓
Определить затронутый бизнес-процесс
 ↓
Обновить бизнес-правило
 ↓
Обновить UX
 ↓
Обновить техническую спецификацию
 ↓
Обновить acceptance criteria
 ↓
Создать или изменить Issue
```

Таким образом документация остаётся актуальной.

# 133. Целевой результат текущего этапа

На текущем этапе необходимо получить не отдельные разрозненные требования, а целостную спецификацию будущей системы.

Результат должен включать:

### Business

Полное описание правил работы.

### Product

Описание всех возможностей и ограничений.

### UX

Полные пользовательские сценарии.

### Architecture

Доменные сущности и связи.

### Data

Полную модель хранения.

### API

Операции и проверки.

### AI

Разрешённые возможности и границы автоматизации.

### Security

Доступ, приватность и защита данных.

### Migration

Переход от текущей структуры к целевой.

### Testing

Проверку требований.

### Implementation

Очередность будущей разработки.

# 134. Главное правило последующей реализации

Будущая разработка должна выполняться **от утверждённой документации к коду**, а не наоборот.

Каждая реализуемая функция должна иметь понятную цепочку:

```text
Зачем функция нужна
        ↓
Что должен получить пользователь
        ↓
Как пользователь выполняет действие
        ↓
Какие бизнес-правила применяются
        ↓
Какие данные необходимы
        ↓
Какая серверная операция выполняется
        ↓
Как выглядит результат
        ↓
Какие ошибки возможны
        ↓
Как результат тестируется
```

Только после фиксации этой цепочки функция должна передаваться в разработку.

# 136. Решение по текущему этапу проекта

На текущем этапе:

**не требуется немедленно реализовывать весь описанный функционал.**

Необходимо:

1. Консолидировать все согласованные пожелания.
2. Устранить противоречия между требованиями.
3. Описать бизнес-логику.
4. Описать UX.
5. Описать техническую модель.
6. Зафиксировать ограничения.
7. Описать миграцию.
8. Описать тестирование.
9. Зафиксировать зависимости.
10. Сформировать единую структуру документации.
11. После утверждения документации сформировать план будущей реализации.

После этого документация становится базовой спецификацией для последующей последовательной разработки функционала.
