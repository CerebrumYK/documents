# BUSINESS RULES

> **Статус документации:** COMPLETE / canonical imported specification  
> **Статус реализации:** `NOT_IMPLEMENTED_AS_SPECIFIED` до подтверждения кодом, миграциями, тестами и runtime evidence согласно `docs/implementation/implementation-status.md` (DOC-207).  
> `✅ Completed` в исходном тексте означает завершённость спецификации, а не реализацию функции.


## Нормативные бизнес-правила профессионального сайта актрисы

**Целевой файл:** `docs/product/business-rules.md`
**Статус:** нормативный документ
**Назначение:** единый каталог бизнес-правил, на которые должны ссылаться UX-сценарии, архитектура, GitHub Issues, проверки и автоматические тесты.

---

# 1. Назначение документа

Настоящий документ определяет **как система обязана вести себя с точки зрения продукта и бизнеса**, независимо от конкретной технической реализации.

Документ не определяет:

* конкретный framework;
* название таблиц базы данных;
* конкретный API transport;
* конкретную библиотеку UI;
* способ физического хранения файлов;
* конкретного AI provider;
* конкретного WhatsApp provider.

Эти решения описываются в технической архитектуре.

Business Rules определяют обязательный результат.

---

# 2. Нормативные термины

В документе используются следующие уровни требований:

### MUST — обязательно

Функция не может считаться реализованной при нарушении правила.

### MUST NOT — запрещено

Поведение системы не допускается.

### SHOULD — рекомендуется

Отклонение допустимо только при документированном обосновании.

### MAY — допустимо

Дополнительная возможность, не являющаяся обязательным условием.

---

# 3. Приоритет правил

Если возникает противоречие между:

1. Business Rules;
2. Functional Requirements;
3. UX specification;
4. Technical Design;
5. GitHub Issue;
6. существующей реализацией;

приоритет имеет более высокий уровень.

Порядок:

```text
Business Rules
      ↓
Functional Requirements
      ↓
Customer Journey / UX
      ↓
Technical Design
      ↓
Implementation Issue
      ↓
Code
```

Если существующий код противоречит настоящему документу, это рассматривается как различие между **AS-IS** и **TO-BE**, а не как причина изменить Business Rule.

# 4. Общие правила системы

## BR-GEN-001 — Единый источник достоверных данных

Каждый профессиональный факт MUST иметь один основной источник хранения.

Например:

* язык хранится в разделе языков;
* навык — в навыках;
* контакт — в контактах;
* проект — в проектах;
* обучение — в курсах и тренингах;
* дата эмоциональной фотосессии — в карточке фотосессии.

Одинаковое значение MUST NOT вручную поддерживаться в нескольких независимых местах.

---

## BR-GEN-002 — Повторное использование данных

Если одно значение используется в нескольких представлениях, система MUST использовать связь с исходной сущностью или зафиксированный snapshot.

Ручное копирование данных между разделами SHOULD быть исключено.

---

## BR-GEN-003 — Разделение Source, Configuration и Derived

Система MUST различать:

1. исходные данные;
2. настройки использования;
3. производный результат.

Изменение производного результата MUST NOT изменять исходные данные.

---

## BR-GEN-004 — Явная публикация

Создание или изменение контента MUST NOT автоматически публиковать его на публичном сайте.

Публикация требует явного разрешённого действия.

---

## BR-GEN-005 — Черновик по умолчанию

Новые профессиональные сущности, имеющие жизненный цикл публикации, SHOULD первоначально создаваться в состоянии Draft.

---

## BR-GEN-006 — Отсутствие неявных побочных эффектов

Действие над одной сущностью MUST NOT изменять независимую сущность, если такой побочный эффект явно не определён Business Rule.

---

## BR-GEN-007 — Один факт вводится один раз

Администратор SHOULD вводить фактическое значение только один раз.

Все доступные связанные представления должны получать его автоматически.

---

## BR-GEN-008 — Публичное представление проектируется одновременно с Admin

Любая профессиональная функция, предназначенная в том числе для внешнего использования, MUST иметь определённое публичное представление.

Нельзя считать функцию завершённой только по наличию административного интерфейса.

---

## BR-GEN-009 — Внутренние функции не обязаны иметь Public UI

Не требуют публичного представления:

* audit;
* внутренние notes;
* системные настройки;
* internal notifications;
* private casting source;
* AI technical metadata;
* миграционные инструменты.

---

## BR-GEN-010 — Профиль как корневая бизнес-сущность

Все профессиональные данные MUST принадлежать конкретному актёрскому профилю.

---

## BR-GEN-011 — Cross-profile связи запрещены

Объект одного профиля MUST NOT быть связан с объектом другого профиля, если специальная межпрофильная модель не определена отдельно.

---

## BR-GEN-012 — Удаление связи не означает удаление источника

Удаление фотографии или другого media item из отдельного раздела MUST NOT автоматически удалять исходный media asset.

---

## BR-GEN-013 — Сохранность опубликованных представлений

Изменение текущих исходных данных MUST NOT незаметно менять ранее зафиксированный immutable опубликованный документ, если для него применяется revision/snapshot model.

---

## BR-GEN-014 — Понятная ошибка пользователю

Бизнес-ошибка MUST отображаться в форме, объясняющей:

* что произошло;
* какой объект затронут;
* что необходимо сделать.

---

## BR-GEN-015 — Невалидное состояние не публикуется

Объект с blocking readiness error MUST NOT переходить в Published.

---

# 5. Правила профиля

## BR-PRF-001 — Профиль является центральным источником профессиональной информации

Публичный сайт, анкеты и кастинговые инструменты MUST использовать данные основного профиля, а не отдельные несвязанные копии.

---

## BR-PRF-002 — Структурированные факты не заменяются биографией

Такие сведения, как:

* языки;
* навыки;
* местоположение;
* профессиональные параметры;

MUST храниться структурированно.

Biography не является источником структурированных фактов.

---

## BR-PRF-003 — Biography является повествовательным контентом

Biography MAY дополнять профиль, но MUST NOT использоваться как единственный источник данных, необходимых для поиска или формирования анкеты.

---

## BR-PRF-004 — Изменение профиля требует проверки зависимостей

Если изменение факта потенциально влияет на draft-анкету или другое производное представление, система SHOULD обозначить зависимые материалы как требующие проверки или пересборки.

---

# 6. Правила Media Library

## BR-MED-001 — Оригинальный файл неизменяем

Загруженный оригинальный media asset MUST сохраняться без изменения содержимого.

---

## BR-MED-002 — Производные версии отдельны

Thumbnail, web image, PDF image, crop и другие производные материалы MUST существовать отдельно от оригинала.

---

## BR-MED-003 — Один файл — множество связей

Один media asset MAY одновременно использоваться:

* в Portfolio;
* Project;
* Emotional Portfolio;
* Questionnaire;
* Training;

без физического копирования.

---

## BR-MED-004 — Удаление используемого оригинала ограничивается

Media asset, используемый опубликованным или значимым зависимым объектом, MUST NOT физически удаляться без проверки зависимостей.

---

## BR-MED-005 — Пользователь должен видеть зависимости

При невозможности удаления система MUST объяснить, где используется материал.

---

## BR-MED-006 — Публичный сайт использует оптимизированные версии

Public gallery SHOULD использовать web/thumbnail derivatives вместо оригиналов максимального размера.

---

## BR-MED-007 — Скрытый media asset не становится публичным через relation

Сам факт связи с другой сущностью MUST NOT обходить правила публикации и доступности файла.

---

# 7. Основное актёрское портфолио

## BR-POR-001 — Portfolio является самостоятельной сущностью

Основное актёрское портфолио MUST существовать отдельно от Projects.

---

## BR-POR-002 — Portfolio отдельно от Emotional Portfolio

Основное Portfolio MUST NOT смешиваться с Emotional Portfolio.

---

## BR-POR-003 — Portfolio показывает профессиональную внешность

Portfolio предназначено прежде всего для постановочных материалов и фотографий, показывающих внешность актрисы.

---

## BR-POR-004 — Поддерживаются профессиональные категории фотографий

Portfolio MUST поддерживать как минимум:

* Full Body;
* Close-Up;
* Waist;
* Profile;
* Three Quarter;
* Staged;
* Appearance;
* Additional.

---

## BR-POR-005 — Full Body выбирается только из Portfolio

Обязательная фотография Full Body для анкеты MUST быть Portfolio Item.

---

## BR-POR-006 — Close-Up выбирается только из Portfolio

Обязательная фотография Close-Up для анкеты MUST быть Portfolio Item.

---

## BR-POR-007 — Media Library не является прямым источником обязательных фотографий

Если фотография существует только в Media Library, перед использованием как обязательная фотография она MUST быть зарегистрирована как Portfolio Item.

---

## BR-POR-008 — Один основной Full Body

Для профиля одновременно SHOULD существовать не более одного основного Full Body.

---

## BR-POR-009 — Один основной Close-Up

Для профиля одновременно SHOULD существовать не более одного основного Close-Up.

---

## BR-POR-010 — Questionnaire может переопределить defaults

Отдельная анкета MAY использовать другую разрешённую фотографию Full Body или Close-Up вместо profile default.

---

## BR-POR-011 — Additional Material назначается независимо

Фотография MAY иметь отдельное разрешение на использование как дополнительный материал анкеты.

---

## BR-POR-012 — Публичная видимость и доступность для анкеты независимы

Фотография MAY:

* отображаться на сайте;
* использоваться в Admin Questionnaire;
* использоваться в Public Builder;

в разных комбинациях согласно установленной policy.

---

## BR-POR-013 — Дата съёмки является сигналом актуальности

Если дата фотографии известна, она SHOULD быть доступна в публичном профессиональном представлении.

---

# 8. Emotional Portfolio

## BR-EMO-001 — Emotional Portfolio является самостоятельным модулем

Emotional Portfolio MUST NOT быть Project.

---

## BR-EMO-002 — Emotional Portfolio не участвует в статистике Projects

Эмоциональная съёмка MUST NOT:

* увеличивать количество проектов;
* попадать в фильтры проектов;
* считаться ролью;
* участвовать в performance chronology.

---

## BR-EMO-003 — Дата съёмки обязательна

Каждое Emotional Portfolio MUST иметь Shooting Date.

---

## BR-EMO-004 — Без даты публикация запрещена

Emotional Portfolio без Shooting Date MUST NOT публиковаться.

---

## BR-EMO-005 — Дата должна использоваться связанными представлениями

Shooting Date MUST быть доступна:

* в Public Emotional Portfolio;
* Emotional Grid;
* Questionnaire;
* PDF.

---

## BR-EMO-006 — Фотографии принадлежат конкретной съёмке

Каждая фотография Emotional Portfolio MUST быть явно связана с конкретной эмоциональной съёмкой.

---

## BR-EMO-007 — Одна фотография может использоваться многократно

Фотография Emotional Portfolio MAY использоваться в нескольких Emotional Grids без физического копирования.

---

## BR-EMO-008 — Полное Emotional Portfolio доступно отдельно от Questionnaire

Questionnaire не обязан включать все emotional photos.

Полный набор доступен через соответствующую Public page, если опубликован.

---

# 9. Emotional Grid

## BR-GRD-001 — Emotional Grid является отдельной сущностью

Emotional Grid MUST существовать отдельно от Emotional Portfolio.

---

## BR-GRD-002 — Grid создаётся из Emotional Portfolio

Каждый Emotional Grid MUST быть связан с исходным Emotional Portfolio.

---

## BR-GRD-003 — Поддерживаемые размеры ограничены

Допустимые варианты:

* 1×2;
* 1×3;
* 1×4;
* 2×2;
* 2×3;
* 2×4;
* 3×2;
* 3×3;
* 3×4;
* 4×2;
* 4×3;
* 4×4.

---

## BR-GRD-004 — Количество заполненных ячеек соответствует размеру Grid

Финальный Grid MUST содержать количество заполненных ячеек, равное rows × columns.

---

## BR-GRD-005 — Каждая ячейка использует реальное исходное фото

Ячейка MUST быть сформирована из разрешённой исходной фотографии.

---

## BR-GRD-006 — Изменение внешности запрещено

При подготовке Grid MUST NOT:

* изменяться лицо;
* изменяться причёска;
* изменяться мимика;
* изменяться возраст;
* изменяться форма тела;
* заменяться одежда;
* добавляться новые элементы изображения.

---

## BR-GRD-007 — Разрешены только геометрические преобразования

Для изображения ячейки MAY использоваться:

* crop;
* scale;
* positioning;
* orientation correction.

---

## BR-GRD-008 — Generative Fill запрещён

Для Emotional Grid MUST NOT использоваться:

* inpainting;
* outpainting;
* generative expansion;
* synthetic face generation.

---

## BR-GRD-009 — Цель крупного плана

Лицо модели SHOULD занимать приблизительно 90% полезной площади каждой ячейки.

---

## BR-GRD-010 — Автоматическая оценка не заменяет человека

Face detection MAY использоваться как подсказка.

Финальная корректность кадрирования MUST подтверждаться человеком.

---

## BR-GRD-011 — Каждая ячейка требует подтверждения

Финализация Grid MUST блокироваться, пока не подтверждены все необходимые ячейки.

---

## BR-GRD-012 — Grid имеет дату исходной съёмки

Emotional Grid MUST использовать Shooting Date соответствующей эмоциональной съёмки.

---

## BR-GRD-013 — Несколько Grid для одной съёмки допустимы

Одно Emotional Portfolio MAY иметь несколько Emotional Grids.

---

## BR-GRD-014 — Основной Grid не означает автоматическое включение

Назначение Grid основным MUST NOT автоматически включать его во все Questionnaires.

---

## BR-GRD-015 — Изменение Grid делает derivatives устаревшими

Изменение crop, фотографии, порядка или размера SHOULD помечать производные версии как stale до нового render.

---

## BR-GRD-016 — Последняя валидная опубликованная версия не должна исчезать до успешного render новой

Неудачная пересборка нового Draft MUST NOT автоматически уничтожать последнюю корректную опубликованную производную версию.

---

# 10. Emotional Grid в анкете

## BR-EQA-001 — В анкете используется composite, а не все фотографии

В блок Questionnaire SHOULD включаться один готовый Emotional Grid вместо полного набора отдельных фотографий.

---

## BR-EQA-002 — В блок входит Shooting Date

Questionnaire MUST показывать дату съёмки Emotional Grid.

---

## BR-EQA-003 — В блок входит ссылка на полное Emotional Portfolio

Если Public Emotional Portfolio доступно, Questionnaire SHOULD содержать кликабельную ссылку.

---

## BR-EQA-004 — Individual emotional photos не добавляются автоматически

Включение Emotional Grid MUST NOT автоматически добавлять все исходные фотографии в Questionnaire.

---

# 11. Projects

## BR-PRJ-001 — Project отражает профессиональный опыт

Project предназначен для реально выполненной или профессионально учитываемой работы актрисы.

---

## BR-PRJ-002 — Courses не являются Projects

Образовательная активность MUST NOT храниться как Project в целевой модели.

---

## BR-PRJ-003 — Emotional Portfolio не является Project

Эмоциональная фотосессия MUST NOT храниться как Project в целевой модели.

---

## BR-PRJ-004 — Project может иметь роли и медиа

Project MAY быть связан:

* с ролями;
* фотографиями;
* видео;
* performance dates;
* достижениями.

---

## BR-PRJ-005 — Избранные проекты могут иметь отдельный публичный приоритет

Public presentation MAY сначала показывать Selected/Featured Projects, а полный список — вторично.

---

## BR-PRJ-006 — Доступность Project в Public Builder определяется явно

Проект MUST быть отдельно разрешён для Public Questionnaire Builder, прежде чем внешний пользователь сможет включить его в свой документ.

---

# 12. Courses & Training

## BR-TRN-001 — Training является самостоятельной бизнес-сущностью

Курсы и тренинги MUST существовать отдельно от Projects.

---

## BR-TRN-002 — Training не участвует в project statistics

Training MUST NOT:

* увеличивать project count;
* попадать в project filters;
* считаться role;
* попадать в project chronology.

---

## BR-TRN-003 — Training может иметь медиа и подтверждения

Training MAY быть связан с:

* certificates;
* documents;
* images;
* video;
* external links.

---

## BR-TRN-004 — Training может быть ongoing

Образовательная запись MAY иметь состояние продолжающегося обучения.

---

## BR-TRN-005 — Отображение Training в Questionnaire выбирается отдельно

Не все курсы обязаны присутствовать в каждой анкете.

---

## BR-TRN-006 — Public Builder видит только разрешённые Training Items

Внешний пользователь MUST NOT получать training items, не разрешённые для Public Builder.

---

# 13. External Links

## BR-LNK-001 — Ссылка является структурированным объектом

Внешняя ссылка MUST иметь как минимум:

* Description;
* URL;
* Order.

---

## BR-LNK-002 — Номер ссылки вычисляется из порядка

Номер SHOULD соответствовать текущему порядку отображения.

---

## BR-LNK-003 — Невалидный URL не должен считаться готовым

Некорректный URL MUST блокировать использование ссылки в готовом документе.

---

## BR-LNK-004 — Ссылка включается в Questionnaire явно

Существование ссылки MUST NOT означать автоматическое включение во все Questionnaires.

---

## BR-LNK-005 — Public Builder видит только разрешённые Links

Внешний пользователь получает только links, разрешённые соответствующей visibility policy.

---

## BR-LNK-006 — PDF hyperlink должен сохранять полный URL

Даже если адрес визуально сокращён, кликабельный target MUST содержать полный разрешённый URL.

---

# 14. Contacts

## BR-CON-001 — Контакты хранятся в едином справочнике

Contact data MUST иметь единый источник.

---

## BR-CON-002 — Поддерживаются обязательные типы

Система MUST поддерживать:

* Phone;
* Mother Phone;
* Father Phone;
* WhatsApp;
* Telegram;
* Instagram;
* TikTok;
* YouTube;
* Other.

---

## BR-CON-003 — Other требует пользовательского названия

Для типа Other MUST быть указано описание типа контакта.

---

## BR-CON-004 — Website Visibility независима от Questionnaire Visibility

Показ контакта на сайте MUST NOT автоматически добавлять его в Questionnaire.

---

## BR-CON-005 — Questionnaire Visibility независима от Website Visibility

Контакт, разрешённый в Admin Questionnaire, MUST NOT автоматически публиковаться на публичной Contact Page.

---

## BR-CON-006 — Public Builder имеет отдельное разрешение

Contact MUST иметь явное разрешение на использование Public Questionnaire Builder.

---

## BR-CON-007 — Родительские контакты не публикуются автоматически

Mother Phone и Father Phone MUST требовать явного разрешения для каждого публичного контекста.

---

## BR-CON-008 — Скрытые контакты не передаются клиенту

Contact, не разрешённый Public Site, MUST NOT присутствовать:

* в HTML;
* public API;
* serialized page state;
* metadata;
* hidden DOM.

---

## BR-CON-009 — Один основной контакт может использоваться как CTA

Профиль MAY иметь Primary Contact для быстрого действия «Связаться».

---

## BR-CON-010 — Основной Contact должен быть активен

Inactive Contact MUST NOT быть Primary.

---

## BR-CON-011 — Контакты в Questionnaire выбираются отдельно по Revision

Каждая Questionnaire Revision MUST иметь собственный набор включённых Contacts.

---

## BR-CON-012 — Контакты должны отображаться компактно

Публичное и PDF-представление SHOULD использовать не более трёх колонок на широком формате.

---

## BR-CON-013 — Иконка не заменяет доступное текстовое описание

Icon-only presentation MUST иметь accessible label.

---

# 15. Questionnaire — общая модель

## BR-QST-001 — Система поддерживает несколько независимых Questionnaires

Один профиль MAY иметь несколько Questionnaire.

---

## BR-QST-002 — Поддерживаются базовые типы

Минимально:

* Compact;
* Extended;
* Casting;
* Custom.

---

## BR-QST-003 — Каждый Questionnaire имеет собственную конфигурацию

Изменение состава одного Questionnaire MUST NOT изменять другой.

---

## BR-QST-004 — Опубликованная Revision immutable

Опубликованная Questionnaire Revision MUST NOT редактироваться непосредственно.

---

## BR-QST-005 — Новое изменение создаёт новую Revision

Изменение опубликованной анкеты MUST приводить к созданию новой редактируемой Revision.

---

## BR-QST-006 — Один Primary Questionnaire

Одновременно для одного профиля MUST быть не более одной основной публичной анкеты.

---

## BR-QST-007 — Primary переключается только на Ready/Publishable Questionnaire

Анкета с blocking readiness errors MUST NOT становиться Primary.

---

## BR-QST-008 — Full Body обязателен

Готовая профессиональная анкета MUST иметь Full Body, если конкретный тип документа явно не освобождён бизнес-правилом.

---

## BR-QST-009 — Close-Up обязателен

Готовая профессиональная анкета MUST иметь Close-Up, если конкретный тип документа явно не освобождён бизнес-правилом.

---

## BR-QST-010 — Full Body и Close-Up происходят из Portfolio

Обязательные фотографии MUST использовать Portfolio Items.

---

## BR-QST-011 — Блоки включаются независимо

Каждая Revision MUST иметь собственный список enabled/disabled blocks.

---

## BR-QST-012 — Порядок блоков является частью Revision

Порядок секций MUST храниться как часть конфигурации Questionnaire Revision.

---

## BR-QST-013 — HTML и PDF используют один логический состав

При одинаковой настройке HTML и PDF MUST представлять один и тот же выбранный набор данных, за исключением особенностей носителя.

---

## BR-QST-014 — Readiness проверяется до публикации

Questionnaire MUST пройти readiness validation.

---

## BR-QST-015 — Пустой обязательный enabled block является ошибкой

Enabled block, который должен содержать данные, MUST NOT оставаться пустым в Ready Questionnaire.

---

## BR-QST-016 — Недоступный media item блокирует или исключается согласно типу зависимости

Если обязательный материал недоступен — публикация MUST блокироваться.

Необязательный материал MAY быть исключён с предупреждением.

---

## BR-QST-017 — Кастинговая Questionnaire не публикуется автоматически

Создание Questionnaire для Casting MUST завершаться в Draft.

---

## BR-QST-018 — Анкета может иметь срок публичной доступности

Questionnaire MAY иметь `available_from` и `available_until`.

---

## BR-QST-019 — Истёкшая анкета не предлагается для нового публичного скачивания

После окончания разрешённого срока Questionnaire MUST исчезнуть из Public Download Picker.

---

## BR-QST-020 — Filename формируется безопасно

Имя PDF MUST быть очищено от недопустимых символов.

---

---

## BR-PDF-005 — Кириллица и поддерживаемые языки отображаются корректно

## BR-PDF-006 — Emotional Grid не деформируется

Grid MUST сохранять пропорции.

---

## BR-PDF-007 — Дата генерации доступна для Public Builder PDF

---

## BR-PDF-008 — Public Builder PDF содержит официальный источник

Документ SHOULD содержать ссылку на актуальный официальный профиль.

## BR-PDF-009 — QR разрешён только на публичный безопасный URL

QR MUST NOT содержать:

* admin credentials;
* permanent secret;
* private data.

Questionnaire за пределами периода доступности MUST NOT отображаться.

# 18. Public Questionnaire Builder

## BR-PQB-001 — Public Builder существует параллельно с готовой анкетой

Наличие Public Builder MUST NOT заменять администраторскую профессионально подготовленную Questionnaire.

---

## BR-PQB-002 — Готовая Questionnaire остаётся рекомендуемой

Public Site SHOULD сначала предлагать рекомендованную версию администратора.

---

## BR-PQB-003 — Public Builder является дополнительным инструментом

Пользователь MAY самостоятельно сформировать другой набор данных, если рекомендованный документ не соответствует его задаче.

---

## BR-PQB-004 — Внешний пользователь не редактирует профиль

Public Builder MUST NOT изменять:

* профиль;
* Portfolio;
* Projects;
* Skills;
* Languages;
* Contacts;
* Admin Questionnaire.

---

## BR-PQB-005 — Пользователь выбирает представление существующих данных

Public Builder работает только как selection/configuration layer.

---

## BR-PQB-006 — Public Builder получает только разрешённые данные

Внешнему пользователю MUST возвращаться только data с соответствующей Public Builder policy.

---

## BR-PQB-007 — Скрытые данные не передаются браузеру

Запрещено загружать полный dataset и скрывать часть элементов только интерфейсом.

---

## BR-PQB-008 — Сервер повторно проверяет каждый выбранный объект

Перед генерацией PDF MUST выполняться server-side revalidation.

---

## BR-PQB-009 — Подмена ID клиентом не должна давать доступ

Пользователь MUST NOT получить запрещённый объект посредством ручной модификации request.

---

## BR-PQB-010 — Public Builder работает без обязательной регистрации

Базовый профессиональный сценарий MUST NOT требовать создания аккаунта.

---

## BR-PQB-011 — Public Builder начинается с шаблона

Пользователь SHOULD начинать с предварительно настроенного template, а не с пустой страницы.

---

## BR-PQB-012 — Минимально поддерживаются Quick, Standard, Extended и Casting

Эти templates MUST быть доступны, если Public Builder включён.

---

## BR-PQB-013 — Template определяет defaults

Template MUST определять:

* default blocks;
* block order;
* limits;
* required blocks.

---

## BR-PQB-014 — Пользователь может убрать разрешённые необязательные блоки

Если block не является Required, пользователь MAY его отключить.

---

## BR-PQB-015 — Пользователь может добавить доступный block

Разрешённый Template/Policy block MAY быть включён пользователем.

---

## BR-PQB-016 — Выбор конкретных элементов поддерживается

Для таких категорий, как:

* Projects;
* Skills;
* Languages;
* Training;
* Additional Photos;
* Links;
* Media;

Public Builder SHOULD позволять item-level selection.

---

## BR-PQB-017 — Пользователь не настраивает дизайн PDF

Public Builder MUST NOT требовать выбора:

* fonts;
* margins;
* цвета;
* размеры заголовков;
* page breaks.

---

## BR-PQB-018 — Layout рассчитывает система

Выбранное содержание MUST автоматически преобразовываться в профессиональный layout.

---

## BR-PQB-019 — Preview доступен до генерации

Пользователь SHOULD иметь возможность проверить состав документа до PDF generation.

---

## BR-PQB-020 — Temporary configuration не становится Admin Questionnaire

Сессия Public Builder MUST NOT появляться в списке постоянных администраторских Questionnaire как обычная Questionnaire.

---

## BR-PQB-021 — Temporary session имеет TTL

Если конфигурация сохраняется сервером, она MUST иметь ограниченный срок жизни.

---

## BR-PQB-022 — Casting Name из Public Builder не изменяет профиль

Введённые внешним пользователем Casting Name и Role используются только в текущем документе/сессии.

---

## BR-PQB-023 — Public Builder не создаёт Casting автоматически

Генерация собственного PDF MUST NOT создавать Casting в административной панели.

---

## BR-PQB-024 — Public Builder PDF имеет официальный источник

Документ MUST позволять вернуться к актуальному профилю.

---

## BR-PQB-025 — Public Builder защищён от массового злоупотребления

MUST применяться разумные ограничения generation rate/session.

---

## BR-PQB-026 — Изменение публичного разрешения влияет на новые генерации

Если item перестал быть разрешён Public Builder, новые PDF MUST NOT его использовать.

---

## BR-PQB-027 — Уже скачанный PDF не может быть отозван технически

Система MUST исходить из того, что локально скачанный PDF остаётся у получателя.

---

## BR-PQB-028 — Типовой Public Builder Journey менее трёх минут

Quick/Standard типовой пользователь SHOULD получать PDF менее чем за три минуты.

---

## BR-PQB-029 — Расширенный Casting Journey менее пяти минут

Подготовленный профессиональный пользователь SHOULD иметь возможность завершить кастомную подборку в пределах пяти минут.

---

## BR-PQB-030 — Готовую Questionnaire можно использовать как стартовую конфигурацию

Пользователь MAY выбрать «Настроить эту версию под себя».

Исходная Questionnaire при этом не меняется.

---

# 19. Castings

## BR-CST-001 — Casting является самостоятельной сущностью

Casting MUST NOT считаться Project актрисы.

---

## BR-CST-002 — Casting хранит входящие требования

Casting используется для хранения и обработки потенциальной профессиональной возможности.

---

## BR-CST-003 — Материалы Casting приватны по умолчанию

Source text, screenshots, briefs и вложения MUST NOT становиться публичными автоматически.

---

## BR-CST-004 — Casting может возникнуть вручную или из Feedback

Администратор MAY:

* создать Casting вручную;
* создать Casting из входящего профессионального обращения.

---

## BR-CST-005 — Создание Casting из Feedback требует решения человека

Feedback MUST NOT автоматически превращаться в Casting.

---

## BR-CST-006 — Исходный Feedback сохраняется

Создание Casting MUST NOT изменять или уничтожать оригинальный текст обращения.

---

## BR-CST-007 — Feedback и Casting имеют двустороннюю связь

Если Casting создан из Feedback, обе сущности SHOULD позволять перейти друг к другу.

---

## BR-CST-008 — Casting Questionnaire связана с конкретным Casting

Анкета, подготовленная для конкретного Casting, SHOULD сохранять такую связь.

---

## BR-CST-009 — Закрытие Casting не удаляет Questionnaire автоматически

Изменение статуса Casting MUST NOT физически уничтожать связанные материалы.

---

# 20. AI Casting Analysis

## BR-AIC-001 — Анализ запускается явно

AI Casting Analysis MUST запускаться после явного действия пользователя или заранее утверждённой автоматизации Draft-only.

---

## BR-AIC-002 — Source Facts хранятся отдельно от AI Extraction

Исходный текст MUST сохраняться независимо от интерпретации ИИ.

---

## BR-AIC-003 — AI Extraction отдельно от Recommendation

Распознанное требование MUST NOT смешиваться с рекомендацией по анкете.

---

## BR-AIC-004 — Human Decision отдельно от AI Recommendation

Подтверждение администратора MUST храниться как отдельное решение.

---

## BR-AIC-005 — ИИ не придумывает отсутствующие требования

Если требование отсутствует в source, система MUST обозначить это как:

«Не указано в материалах кастинга».

---

## BR-AIC-006 — Предположение не выдаётся за факт

Низкоуверенный вывод MUST быть обозначен как требующий проверки.

---

## BR-AIC-007 — Confidence сохраняется

Каждый extracted requirement SHOULD иметь confidence/status.

---

## BR-AIC-008 — Профиль не изменяется автоматически

AI Casting Analysis MUST NOT добавлять новые:

* Skills;
* Languages;
* Roles;
* Experience;
* physical facts;

в основной профиль.

---

## BR-AIC-009 — Recommendation объясняется

Каждая существенная рекомендация SHOULD иметь причину.

---

## BR-AIC-010 — Recommendation ссылается на требование

Где применимо, рекомендация SHOULD указывать, какое Casting Requirement её вызвало.

---

## BR-AIC-011 — Созданная AI Questionnaire остаётся Draft

Автоматически подготовленная анкета MUST требовать проверки человека.

---

## BR-AIC-012 — Reanalysis создаёт новую версию анализа

Повторный анализ MUST NOT бесследно заменять предыдущий результат.

---

# 21. Feedback

## BR-FDB-001 — Public Feedback является профессиональным каналом связи

Feedback Form MUST поддерживать профессиональные типы обращения.

---

## BR-FDB-002 — Минимально поддерживаются основные намерения

Минимально:

* Casting Invitation;
* Role Offer;
* Collaboration;
* Questionnaire Request;
* Additional Materials;
* Question;
* Comment;
* Other.

---

## BR-FDB-003 — Feedback сохраняется до внешних уведомлений

Запись MUST быть успешно сохранена до попытки WhatsApp или другого внешнего notification.

---

## BR-FDB-004 — Ошибка WhatsApp не отменяет Feedback

Неудача внешнего уведомления MUST NOT приводить к потере принятого обращения.

---

## BR-FDB-005 — Feedback получает понятный публичный номер

После успешной отправки пользователь SHOULD получить reference number.

---

## BR-FDB-006 — Требуется хотя бы один способ ответа

Профессиональное обращение MUST содержать хотя бы один разрешённый контакт для ответа.

---

## BR-FDB-007 — Согласие обязательно, если собираются персональные данные

Public Form MUST требовать предусмотренное продуктом согласие.

---

## BR-FDB-008 — Двойная отправка не должна создавать дубликаты

Повтор одного и того же submission SHOULD обрабатываться идемпотентно.

---

## BR-FDB-009 — Ошибка формы не очищает введённые данные без необходимости

При исправимой ошибке пользователь SHOULD сохранить уже введённую информацию.

---

## BR-FDB-010 — Attachment приватен

Вложение Feedback MUST NOT иметь открытый публичный URL.

---

## BR-FDB-011 — Опасный Attachment блокируется

Недопустимый файл MUST быть отклонён.

---

## BR-FDB-012 — Workflow Status независим от Read Status

`unread/read` MUST храниться отдельно от:

* new;
* in progress;
* completed;
* и других workflow statuses.

---

## BR-FDB-013 — Internal Note не видна отправителю

Административные notes MUST оставаться внутренними.

---

## BR-FDB-014 — Feedback может иметь ответственное лицо

Система MAY поддерживать assignment.

---

## BR-FDB-015 — Feedback может иметь Next Action

Система MAY поддерживать дату следующего действия для контроля follow-up.

---

# 22. Notifications

## BR-NOT-001 — Внутреннее уведомление создаётся независимо от WhatsApp

Internal notification MUST NOT зависеть от успешности external notification.

---

## BR-NOT-002 — WhatsApp является дополнительным каналом

WhatsApp не является единственным источником информации о новом Feedback.

---

## BR-NOT-003 — Минимизировать данные WhatsApp

По умолчанию notification SHOULD содержать только минимально необходимый объём.

---

## BR-NOT-004 — Полный Feedback не отправляется в WhatsApp по умолчанию

Полный message и attachments MUST NOT пересылаться автоматически.

---

## BR-NOT-005 — Admin Link защищён

Notification link MUST вести на защищённую административную страницу.

---

## BR-NOT-006 — URL не содержит PII

Protected Admin Link MUST NOT содержать персональные данные в query/path без необходимости.

---

## BR-NOT-007 — Notification идемпотентен

---

## BR-NOT-008 — Retry ограничен

---

## BR-NOT-009 — Permanent Failure виден в Admin

---

## BR-NOT-010 — Quiet Hours не задерживают сохранение Feedback

Период тишины MAY задерживать внешний notification, но Feedback сохраняется немедленно.

---

# 23. Opportunity Pipeline

---

## BR-OPP-004 — Outcome может обновляться вручную

# 24. Customer Journey

## BR-CJM-001 — Публичный сайт оптимизируется под профессиональное решение

Цель сайта — не максимизация времени просмотра, а сокращение времени до обоснованного профессионального действия.

---

## BR-CJM-002 — Casting Director должен быстро определить соответствие

Основные сведения MUST быть доступны без изучения всей структуры сайта.

# 41. Трассируемость Business Rules

Каждое правило настоящего документа должно в дальнейшем быть связано минимум с одним из следующих артефактов:

* Functional Requirement;
* UX Flow;
* Technical Requirement;
* GitHub Issue;
* Automated Test.

Для критических правил рекомендуется полная цепочка:

```text
Business Rule
    ↓
Functional Requirement
    ↓
UX Flow
    ↓
Implementation Issue
    ↓
Automated Test
```

Пример:

```text
BR-PQB-006
Public Builder получает только разрешённые данные

    ↓

FR-PQB-012
Фильтрация разрешённых сущностей

    ↓

UF-PQB-003
Выбор Project

    ↓

TASK-PQB-014
Implement public data policy

    ↓

IT-PQB-006
Forbidden project ID rejected
```

# 43. Сводка ключевых непреложных правил

Следующие правила являются центральными для всей архитектуры продукта:

1. Профиль является Single Source of Truth.
2. Оригинальные media assets не изменяются.
3. Portfolio отдельно от Projects.
4. Emotional Portfolio отдельно от Projects.
5. Training отдельно от Projects.
6. Full Body и Close-Up происходят из Portfolio.
7. Emotional Grid строится только из реальных исходных фотографий.
8. Внешность модели при создании Grid не изменяется.
9. Shooting Date Emotional Portfolio обязательна.
10. Questionnaire использует один composite Emotional Grid вместо полного набора emotional photos.
11. Published Questionnaire Revision immutable.
12. Готовая Questionnaire администратора является основным рекомендуемым документом.
13. Public Questionnaire Builder существует дополнительно к ней.
14. Public Builder не изменяет Profile.
15. Public Builder получает только явно разрешённые данные.
16. Hidden data не передаются браузеру.
17. Public Builder повторно валидирует selections сервером.
18. Casting является самостоятельной сущностью.
19. ИИ не придумывает фактические требования Casting.
20. AI Recommendation требует human control.
21. Feedback сохраняется до отправки WhatsApp.
22. Ошибка WhatsApp не приводит к потере Feedback.
23. Feedback не становится Casting автоматически.
24. Site Theme изменяет presentation, а не content.
25. AI Theme не публикуется автоматически.
26. Virtual Operator работает как Draft/Recommendation assistant.
27. Virtual Operator не меняет факты самостоятельно.
28. Customer Journey оптимизируется на быстрый профессиональный результат.
29. Сайт должен сокращать путь от интереса к Casting Invitation.
30. Все критические Business Rules должны быть покрыты тестами.
